# `sdk_example_scene` — Weather plugin (v1.1.0 reference)

Fully-buildable reference plugin built against the v1.1.0 Plugin SDK.
Shows what a real third-party plugin looks like end-to-end:

- One scene (`scene_weather`) registered via `PLUGIN_SCENE_REGISTER`.
- Two console verbs (`plugin.weather.set_city`, `plugin.weather.refresh`).
- Read-only access to `agent_state` via `plugin_agent_state_borrow_const`
  to demonstrate situational awareness ("agents are busy" hint).
- Lifecycle: `on_init` / `on_show` / `on_hide` / `frame` / `on_dash`.

## Stub data contract

The dashboard bridge does NOT currently fetch real weather. The
plugin ships with a built-in 4-day fake forecast (see `FAKE_FORECAST`
in `scene_weather.c`). The contract for replacing it later:

- Bridge MAY push real data via
  `dash plugin weather refresh "{<forecast json>}"`.
- The plugin's `on_dash("refresh", ...)` handler is the single
  ingestion point.
- If the bridge never pushes, the plugin renders its built-in fakes,
  so the scene is meaningful offline.

When v1.4.0+ (or earlier) wires a real weather fetcher in the bridge,
this plugin needs **no firmware change** — that's the entire point of
having the SDK.

## Building (as a fork)

This example is intentionally NOT compiled into the default firmware
(per PLUG1's hard rule against modifying `main/CMakeLists.txt`
ahead of cycle). To opt in from a fork:

```cmake
# top-level CMakeLists.txt — before project(...)
list(APPEND EXTRA_COMPONENT_DIRS examples/sdk_example_scene)
```

Then:

```
python tools/sdk/sign_plugin.py examples/sdk_example_scene --self-trust
idf.py build flash monitor
```

You should see (paraphrased):

```
I (...) plugin_loader: accepted [weather] abi=1
EVT: plugin_loaded name=weather abi=1
```

And `dash plugin weather refresh` should round-trip.

If you see:

```
E (...) plugin_loader: reject [weather]: author signature failed
EVT: plugin_reject name=weather reason=sig_author
```

that's the safe failure mode — run `sign_plugin.py` first.
