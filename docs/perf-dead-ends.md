# 渲染性能：走过的死路与实测常数

**在开始任何新的渲染优化之前读一遍这份。** 下面每一条都在这块板子上实测
过（ESP32-S3 + CO5300 QSPI AMOLED 466×466，LVGL 9，软件渲染）。

先说唯一一条主干规律，四次独立实验都指向它：

> **渲染成本跟着"要重新生成多少内容"走，不跟着"弄脏了多大面积"走。**
>
> 面积只是账单的一半，另一半是"这块面积上压着多少个需要重新光栅化的
> 对象"。三条死路都是因为只优化了面积那一半。

---

## 一、走不通的路（不要重试，除非有新证据）

### 1. 开第二个软件绘制单元（用上第二个核）

`CONFIG_LV_DRAW_SW_DRAW_UNIT_CNT=2`

| 场景 | 单绘制单元 | 双绘制单元 |
|---|---|---|
| clock 转场 | 21.7 ms/帧 | **30.8 ms/帧** |
| weather 转场 | 38.9 ms/帧 | **53.9 ms/帧** |
| dashboard 转场 | 21.5 ms/帧 | **29.5 ms/帧** |

帧率再降约 15%，而且**设备在测量中重启**。

原因：绘制缓冲只有 28 行（后来 56 行），每次刷新被切成很多小块，每块的
绘制任务太碎——跨线程派发 + LVGL 主任务等待两个单元的开销超过并行收益。
另外多出的 8KB 绘制线程栈会挤压只有 ~56KB 余量的内部 RAM。

**结论：瓶颈是像素总量，不是核心数。** 除非缓冲区能大到让每块的绘制任务
足够重，否则并行没有意义。

### 2. 转场期间整屏合并脏区

在 `LV_EVENT_REFR_START` 里 `lv_obj_invalidate(screen)`，把一帧里 20+ 个
互不重叠的脏矩形折成一个整屏区域。

动机看起来很有道理：每帧脏 34~83 万像素，而整屏才 21.7 万，整屏画一次
应该更便宜。

| 场景 | 合并前 | 合并后 |
|---|---|---|
| clock 转场 | 14.7 ms/帧 | **29.7 ms/帧** |
| weather 转场 | 20.9 ms/帧 | **32.6 ms/帧** |
| 掉帧数 | 1 | **17** |

**这条是主干规律的直接反例，也是它的来源。** 脏矩形小的时候，落在里面的
对象少；整屏失效等于强制把屏幕上每一个对象都重画一遍，包括天气那 30 条
抗锯齿线段、脉冲圆环、圆角卡片这些昂贵图元。

### 3. 给"内容稀疏"的演员做精灵烘焙

见下节。烘焙本身有效，但用错地方是负优化。

### 4. 关掉未使用的 WiFi / 裁剪未引用的字体

两条都基于"它们在占资源"的假设，实测**都不占**：

- 翻转 `CONFIG_ESP_WIFI_ENABLED` 镜像大小变化 **0 字节**（2939541 两边
  一样）。静态 DRAM 总共只有 `.data 14KB + .bss 13KB`，`-ffunction-sections`
  早就把未引用的 WiFi 静态量丢掉了。而且这个符号会被依赖图重新推导，
  sdkconfig 里写一行根本不生效。
- 8 个 `LV_FONT_MONTSERRAT_*` 里只有 4 个被引用，但**未引用的字模压根不在
  .map 里**。Kconfig 里 enabled ≠ 实际链接。

**教训：动手前先量。** 这两条我都是先断言后测量，两次都错。

## 二、有效的路（附实测收益）

| 手段 | 收益 | 备注 |
|---|---|---|
| 绘制缓冲 28 行 → 56 行 | render 砍半（24.6→14.7 / 42.5→20.9 ms） | 分块数 17→9，每块都要重走一遍对象树 |
| 动态刷新率（转场 16ms / 静止 66ms） | 转场 30fps → 44~58fps | **收益最大**：render 只要 20ms 而周期是 33ms，每帧画完白等 13ms |
| 转场期间冻结环境动画 | 见上（含在缓冲那一项里） | 天气插画呼吸、时钟冒号闪，转场里看不见但照样烧预算 |
| 批量失效（关自动 refresh + 手动失效小块） | 天气呼吸脏区 115k→27k px；边框辉光 53.4→18.5 ms/帧 | 但**渲染时间只降 6%**——又一次印证主干规律 |
| 精灵烘焙（内容密集的演员） | weather 转场 38.5→32.0 ms | 见下方的适用边界 |

### 精灵烘焙的适用边界

把运动中的演员在运动前光栅化成位图，运动期间只 blit。

**只在"内容成本 / 面积"比值高时划算：**

| 演员 | 烘焙前 | 烘焙后 | 结论 |
|---|---|---|---|
| weather 的演员（30 条抗锯齿线 + 15 个标签） | 38.5 ms | **32.0 ms** | 赢 17% |
| dashboard 的 ambient 簇（466×224 容器，内含一个 96px 圆环 + 两行字） | **21.8 ms** | 26.6 ms | 输 23% |

ambient 簇绝大部分是空像素，烘焙它等于每帧从 PSRAM 搬 417KB 近乎全透明
的 ARGB8888，去替代画三个廉价对象。

**⚠️ 当前默认关闭**（`?bake 1` 可开）：它会让设备 panic 重启。复现：天气
场景上 PWR 往返（weather↔clock）350ms 间隔，第 1 轮就崩。二分证据干净
（`?bake 0` 撑过 20 轮，`?bake 1` 第 1 轮崩）。只在 clock↔weather 这一对
出现——那是唯一**两侧都有时间锚点变形回调**的组合，6 张 ARGB8888 快照要和
对侧的字号档位变形并发。根因未定位到具体行。

## 三、容易踩的实现坑

1. **快照颜色格式必须同时在两张白名单里**：`lv_snapshot.c` 的 switch，以及
   `CONFIG_LV_DRAW_SW_SUPPORT_*`。`RGB565A8` 只在第二张 → `lv_snapshot_take`
   直接返回 NULL。这让"精灵烘焙"整整一个版本**从未真正运行过**，而期间的
   A/B 两条臂跑的是同一份代码，那个"5~15% 收益"是纯漂移。
   **有静默降级的地方，一定要 WARN 出来。**

2. **快照缓冲不是本体那么大**：尺寸是 `obj + 2*ext_draw`，内容原点是
   `obj.coords.x1 - ext`。按 align + style x/y 摆替身会错位（TOP_MID 居中
   时 x 凑巧对上、y 差一个 ext），转场收尾换回本体那一帧元素会当场跳。

3. **贴边绘制要用可见区，不是 LVGL 坐标空间**：LVGL 是 480×480，物理面板
   只有 466×466，且原点还有个没写在任何配置里的偏移。见 `ui_screen.h`。

4. **圆角元素的失效带要按圆弧算**：直边处墨迹深 21px，但 45° 角落处深
   26.1px。按直边算会让四个角永远刷不到，表现为"发光在拐角断开"。

5. **`lv_obj_enable_style_refresh(false)` 中间不能 early return**：会让整个
   UI 永久停止刷新。用 `ui_motion_batch_begin/end`，它强制配对。

6. **不要每帧动大 tiny_ttf 标签的 size / transform_scale / widget-opa**：
   跑马灯冻结、时钟 plan A、overview 环呼吸、prompt 脉动都是这么死的。
   用场景 tick 做低频步进。

## 四、量东西的工具

| 命令 | 用途 |
|---|---|
| `?perf` | render / flush-wait / 脏像素 / 掉帧，窗口式（读取即清零）。**看 `frame_ms` 不要看 `fps_win`**——后者会被空闲尾巴稀释 |
| `?stat` | `fps` 是真的（LV_EVENT_RENDER_READY）；`reset_reason` 能活过重启，崩溃后可查 |
| `?bake 0\|1` | 精灵烘焙 A/B |
| `?refr <ms>` | 静止档刷新周期 |
| `?wxbreath 0\|1` | 天气插画呼吸波形 A/B |
| `?ghost` | 转场替身的几何自检（mismatched 必须为 0） |
| `& ./tools/with_port.ps1 { ... }` | 独占串口跑任意脚本块，防 hook 抢端口打断测量 |

**单次转场的渲染耗时噪声能到 60%。** 至少跑 4 次重复、交替两条臂再下结论
——我从噪声里读出过一个不存在的 15% 收益，还写进了提交信息。
